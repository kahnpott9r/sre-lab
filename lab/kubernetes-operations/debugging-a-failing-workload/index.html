Lesson 03

Debugging a failing workload

Six status strings cover almost every broken pod. Learn what each one is telling you and the first command to run.

28m1 lab

By the end of this lesson you can

  • Classify a failing pod by its status string
  • Choose the right diagnostic command for each failure class
  • Recognise resource-limit problems from scheduling and runtime evidence
  • Avoid the debug moves that make an outage worse

Status strings are the diagnosis

A pod's status is not a generic "something is wrong" — each string names a distinct failure class with its own first command:

StatusMeaningFirst command
PendingNo node accepted it, or the image is still being pulledkubectl describe pod → events
ContainerCreatingRuntime is setting up; stuck means volumes/networkkubectl describe pod
ImagePullBackOffEvery pull attempt failedkubectl describe pod → registry error
CrashLoopBackOffContainer starts and exits, repeatedly, with backoffkubectl logs --previous, exit code
Running / not ReadyProcess is up, probe is failingkubectl describe pod → probe messages
Terminating (stuck)Finalizers, or a graceful period that never endskubectl get pod -o yaml → finalizers
OOMKilled (in Last State)cgroup memory limit exceededRaise the limit or fix the leak

Two commands answer almost everything:

Tip

kubectl get pods -w is underused. Watching a pod go Pending → ContainerCreating → Running → CrashLoopBackOff gives you the shape of the failure in real time. describe gives you the same story after the fact, and both beat guessing.

CrashLoopBackOff: read the exit code

The status name is slightly misleading — Backoff refers to the restart schedule, not the cause. Kubernetes doubles the delay each time (10s, 20s, 40s, up to 5 minutes), which is why a broken pod seems to "restart every few minutes" rather than continuously.

kubectl logs shows the current container, which may have written nothing if it died immediately. Reach for the previous instance:

Then translate the exit code:

CodeCauseFix direction
0Process exited cleanly — the command is wrongThe entrypoint should run in the foreground
1Application errorRead the logs; usually config or a missing dependency
127Command not foundWrong entrypoint path, or the binary is not in the image
137SIGKILL / OOMKilledRaise the memory limit or fix the leak
143SIGTERM — graceful stopSomething is telling it to stop (check the shutdown period)

Note that 127 is nearly always a local build problem dressed as a cluster problem: an image that works on your laptop and not in the cluster usually has a different entrypoint or a missing binary in the final build stage.

Pending: the scheduler's reason

Pending means the pod object exists but no node was assigned. The scheduler refuses for a short list of reasons, and describe names the exact one:

Events:
  Warning  FailedScheduling  0/3 nodes are available:
           1 Insufficient cpu, 1 node(s) had untolerated taint,
           1 node(s) didn't match Pod's node affinity.

The crucial detail is that the scheduler decides using requests, not limits and not live utilisation:

So a node at 20% CPU with no free reserved capacity will refuse a pod. This is why "the nodes look idle, why is it Pending?" is not a contradiction — it means other pods have reserved the capacity.

Watch out

Omitting requests entirely makes scheduling unreliable: every pod can be packed onto one node until the kernel starts refusing work. Always set both, and set requests to what the workload genuinely needs at steady state.

"Running and Ready" means Kubernetes is satisfied

This is the most frustrating class of failure, because every Kubernetes-level signal is green:

  • the container is Running and Ready;
  • the Deployment reports all replicas available;
  • the Service has endpoints.

If users still see errors, the fault is inside the application or its dependencies, and Kubernetes has no opinion about it. A readiness probe that only checks "can I open a socket on port 8080?" will report Ready while the app returns 500 to every real request.

Then improve the probe so the next incident is detectable. A readiness endpoint that checks its actual dependencies converts a silent 500 generator into a pod that never receives traffic.

The debugging moves that make things worse

Some intuitive actions destroy information or amplify the failure:

Don'tWhyDo instead
kubectl delete pod firstLoses logs and container state; the controller recreates the same breakagekubectl logs --previous and describe first
Increase replicas to "spread the load"Multiplies whatever is wrong across more instancesFix the one broken instance
kubectl rollout restart immediatelyReplaces every instance, losing the broken ones' evidenceRead the current failure, then restart with a hypothesis
Raise the memory limit reflexivelyIf it is a leak, you have bought hours and hidden the trendCheck whether usage is growing or spiky
Set the liveness probe more aggressivelyTurns a slow pod into a restart loopUse a startup probe and relax liveness

A repeatable order of operations

Only after those four do you change anything. The discipline is what keeps a brownout from becoming an outage — and the evidence you gather is exactly what the postmortem will need.

Command cheat sheet

Each entry is the syntax, a real invocation with the output to expect, the failure it hides and where it behaves differently on another system.

kubectl get pods -w

Watch status transitions live — the order of events is the clue.

kubectl describe pod <name>

Spec, conditions and the event log at the bottom.

kubectl logs <pod> --previous

Logs from the crashed instance — use this for CrashLoopBackOff.

kubectl get events --sort-by=.lastTimestamp

Cluster-wide timeline, newest last.

kubectl exec -it <pod> -- sh

Get a shell inside a running container.
