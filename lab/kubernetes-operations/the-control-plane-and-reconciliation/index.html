Lesson 01

The control plane and the reconciliation loop

Nothing in Kubernetes "starts" your container. A loop notices a difference between desired and actual and works to close it.

22m1 lab

By the end of this lesson you can

  • Describe the desired-state model and the reconciliation loop
  • Name the control-plane components and what each one owns
  • Explain what etcd being unavailable actually costs you
  • Predict why a deleted pod comes back

Desired state, not commands

Almost every surprise in Kubernetes comes from forgetting this:

You never start a container. You declare what should exist, and a controller works to make it so.

A Deployment says "there should be 3 pods running image app:1.4". The story from there is a loop:

      ┌──────────────────────────────┐
      │  desired state (etcd)        │
      │  Deployment: replicas = 3    │
      └──────────────┬───────────────┘
                     │ watch
      ┌──────────────▼───────────────┐
      │  controller observes reality │
      │  actual: 2 pods ready        │
      └──────────────┬───────────────┘
                     │ difference detected
      ┌──────────────▼───────────────┐
      │  act: create 1 more pod      │
      └──────────────┬───────────────┘
                     │
                     └──────── repeats forever ────────┐
                                                       │

Nothing in that loop is a "start command" that runs once. It runs continuously. That single fact explains:

  • Why deleting a pod is not a permanent fix — the controller recreates it.
  • Why editing a live pod by hand is pointless — the next reconcile overwrites it.
  • Why "self-healing" is not a feature but a consequence of the design.

Who owns what

ComponentRuns onOwns
kube-apiserverControl planeThe only gateway to etcd; validation, admission, watch
etcdControl planeAll cluster state. The thing you must back up
kube-schedulerControl planeDeciding which node a Pod runs on
kube-controller-managerControl planeThe built-in loops: ReplicaSet, Node, Job, Endpoints
cloud-controller-managerControl planeCloud integration: load balancers, node lifecycle
kubeletEvery nodeMaking containers match the PodSpecs assigned to it
kube-proxyEvery nodeProgramming Service routing rules in the dataplane

Read the table top-down as "who decides" and bottom-up as "who acts". The split is what lets the control plane go down without stopping your traffic.

The API server is the constraint

Only the API server talks to etcd. Everything else — controllers, scheduler, kubelet, kubectl — goes through it. So "is the control plane healthy?" is really one question:

If the API server is up, controllers will converge. If it is not:

  • Existing pods keep running. kubelet and the container runtime are local and do not need the API server to keep containers alive.
  • Nothing new can be declared. kubectl apply blocks or fails.
  • Self-healing stops for node-level failures. A node that dies will not have its pods rescheduled, because nothing can record that decision.
  • Rollouts freeze mid-flight, potentially leaving a Deployment with a mix of old and new ReplicaSets.

That is a real outage, and it will not show up in your request-level error rate. Availability of serving and availability of changing are different SLOs, and you should measure both.

Note

kubectl get componentstatuses is deprecated on modern clusters and may return nothing useful. /readyz and /livez on the API server, plus the control-plane pods' own status if you run them as static pods, are the supported signals.

Why hand-editing a pod never works

A Pod is mostly immutable where it matters — image, resources, volumes. You can edit some fields, but the ReplicaSet controller owns that Pod, and its spec says otherwise. The controller will create a replacement from the ReplicaSet template, and your edit is lost.

The fix is always one level up: edit the Deployment, let it create a new ReplicaSet, and let the rollout controller replace pods gradually. This is the mental move that separates people who fight Kubernetes from people who use it:

When a resource does not do what you want, change the thing that owns it.

Command cheat sheet

Each entry is the syntax, a real invocation with the output to expect, the failure it hides and where it behaves differently on another system.

kubectl get componentstatuses

Health of the control-plane components.

kubectl get --raw /readyz

The API server's own readiness endpoint.

kubectl get pods -A

Everything running, across namespaces.

kubectl describe <res>

Spec plus the events that explain the current state.
