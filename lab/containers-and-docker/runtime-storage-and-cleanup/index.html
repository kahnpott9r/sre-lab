Lesson 03

Runtime, storage and cleanup

A container that exits immediately is telling you something specific. Learn to read the four messages, and to know where the data went.

25m1 lab

By the end of this lesson you can

  • Read a container's exit code as evidence rather than noise
  • Separate container filesystem lifetime from volume lifetime
  • Use docker inspect to find the real cause of an exit
  • Clean up without deleting the thing you will need during the incident

A container lives exactly as long as PID 1

This is the fact that explains most confusing container behaviour. There is no init process keeping the lights on: the process you start is the container. When it exits, the container stops, and the exit code is preserved as evidence.

That is why Dockerfiles end with CMD ["node", "server.js"] and not CMD service node start. A wrapper that daemonises forks into the background, the foreground process exits immediately, and Docker dutifully declares the container finished. The workload is running — outside the container's lifetime. This is the classic "helpful" init script bug.

Read the exit code before the logs

Exit codes are precise. Learn the four that cover most incidents:

CodeMeaningFirst thing to check
0Process finished successfullyThe command was wrong — it was not meant to run and exit
1Application errorThe logs, which will be non-empty
126Command found but not executableA missing chmod +x, or wrong file mode on the entrypoint
127Command not foundBad CMD/ENTRYPOINT path, or a binary absent from the image
137SIGKILL — 128 + 9Memory limit, or an external kill
143SIGTERM — 128 + 15A graceful shutdown was requested (deploy, docker stop)

Tip

143 is not a crash. It means the process received SIGTERM and handled it — for example because you ran docker stop. Plenty of incidents have been opened against a container that was doing exactly what it was told.

Where the data actually lives

Three different things get called "storage", and they behave completely differently:

MechanismLives whereSurvives docker rmUse for
Writable layerInside the containerNoNothing you care about
Named volumeManaged by Docker, outside the containerYesDatabases, persistent state
Bind mountA path on the hostYesConfig files, local development

The first row is the trap. A container's writable layer is created when the container starts and discarded when the container is removed. Recreate the container from a newer image and the data is not "still there but hidden" — it is gone.

Now the bytes are in the pgdata volume, which has a lifecycle independent of any container. docker rm db leaves the volume untouched; a new container can mount the same volume and find the database waiting.

Watch out

This cuts both ways. A named volume that outlives its container accumulates forever if nothing cleans it up, and docker volume rm is not recoverable. Treat volumes as production data: back them up, name them purposefully, and never remove one during an incident to free space.

Restart policies are not a health mechanism

A restart policy keeps a crashing container crashing — it just adds a loop. The container restarts, fails, restarts, fails, and you get a restart count climbing in docker inspect rather than a working service. Read it as a signal:

Command cheat sheet

Each entry is the syntax, a real invocation with the output to expect, the failure it hides and where it behaves differently on another system.

docker run -d --name app nginx

Start detached with a stable name you can refer to.

docker ps -a

Include exited containers — that is where the evidence is.

docker logs <ctr>

Whatever the process wrote to stdout and stderr.

docker inspect --format '{{.State.ExitCode}}'

The exit code without scrolling through JSON.

docker run -v appdata:/data

Mount a named volume so data survives the container.
