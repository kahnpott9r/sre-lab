Lesson 01

What a container actually is

There is no container in the Linux kernel. There are namespaces, cgroups and a process that has been lied to about what it can see.

20m1 lab

By the end of this lesson you can

  • Distinguish a container from a virtual machine
  • Name the namespaces that isolate a workload and what each one hides
  • Explain what cgroups limit and what they do not
  • Predict what breaks when a container assumes it has its own kernel

Start with the honest sentence

A container is a normal Linux process that the kernel has been told to hide parts of the world from, plus a set of resource limits attached to it. That is the whole idea.

unshare is a coreutil. It creates new namespaces and runs a command inside them. When you understand unshare, Docker stops being magic and becomes a convenient wrapper over a well-defined kernel API.

Namespaces: what the process cannot see

A namespace is a view. Each type hides one category of thing:

NamespaceHidesPractical effect
pidProcess IDsPID 1 inside is not PID 1 on the host
mntMount pointsIts own /, and no access to the host's files
netNetwork interfaces, routes, portsIts own eth0 and its own port space
utsHostname and domainhostname returns whatever the container sets
ipcSysV IPC, POSIX queuesShared memory does not leak between containers
userUID/GID mappingRoot inside can be an unprivileged UID outside

That table answers a lot of operational questions before you have to google them:

  • Two containers can both bind port 80 — each has its own network namespace, so each has its own port space.
  • Setting the hostname inside a container does not affect the host — different UTS namespace.
  • A container that is "root" is often not root on the host — the user namespace maps it to an unprivileged UID.

Watch out

The user namespace is not always enabled. Without it (or with --privileged), a process that breaks out of the container is genuinely root on the host. This is why "just run it privileged" is a security decision, not a convenience one.

cgroups: what the process cannot consume

Namespaces are about visibility. cgroups are about accounting and limiting:

  • CPU — shares, quota, or a hard cap in cores
  • memory — soft limit (reclaim pressure) and hard limit (OOM kill)
  • blkio — read/write bandwidth and IOPS
  • pids — maximum number of processes

The memory limit is the one that wakes people up. When a cgroup reaches its hard limit, the kernel first tries to reclaim page cache. If it cannot, it invokes the OOM killer against that cgroup and kills a process in it. Your container's main process is the usual victim, and the exit code is:

137 = 128 + 9   →  terminated by SIGKILL

So Exited (137) plus a memory limit in docker inspect is not a mystery. It is the kernel telling you that you asked for 512Mi and the workload needed more.

The immutable-kernel line

This is the distinction that matters most in practice:

ContainerVirtual machine
KernelShared with hostIts own
Boot timeMillisecondsSeconds to minutes
Memory overheadProcess + limitsFull kernel, own page cache
UserspaceWhatever is in the imageWhatever is in the disk image
Can load kernel modulesNoYes
Isolation strengthNamespaces + capabilitiesHardware virtualisation

Two containers can run images with completely different glibc versions, because glibc is just a file inside each image. Two VMs are needed when you genuinely need a different kernel — a different version, different modules, or a different patch level.

Why this matters at 3am

The model predicts the failures:

  • uname -r differs from the image's base distro → expected, the kernel is the host's. Do not chase it.
  • A workload needs a kernel module → it cannot be containerised without giving up the isolation that made containers useful.
  • Killed with 137 → look at the cgroup memory limit before you look at the application.
  • Data vanished on restart → the container's filesystem is a writable layer that is discarded with the container. State needs a volume, and that is the subject of the next lesson.

Check yourself

The lab is a quiz on the model rather than the CLI. Answering these correctly is what lets you skip the twelve tabs of documentation when a container dies at 03:00.

Command cheat sheet

Each entry is the syntax, a real invocation with the output to expect, the failure it hides and where it behaves differently on another system.

unshare --pid --fork

Create a new PID namespace for a child process.

lsns

List the namespaces visible on the host.

cat /proc/self/cgroup

Show which cgroup a process is attached to.

docker inspect <ctr>

Full configuration, including resource limits.
