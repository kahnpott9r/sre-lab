Lesson 02

Images, layers and the build cache

An image is a stack of tarballs and a JSON document. The order you write your Dockerfile in decides whether your builds take 8 seconds or 8 minutes.

25m1 lab

By the end of this lesson you can

  • Describe an image as an ordered stack of immutable layers
  • Predict which instructions invalidate the build cache
  • Order a Dockerfile so the slow steps are cached
  • Explain why an image can be large even when the container is small

An image is a stack, not a snapshot

Think of an image as a short stack of read-only tarballs plus a small JSON document. Each instruction in your Dockerfile that changes the filesystem produces exactly one new layer containing only the changed files.

IMAGE   CREATED BY                        SIZE
a1b2c3  CMD ["node" "server.js"]          0B
d4e5f6  COPY src ./src                    412kB
789abc  RUN npm ci --omit=dev            141MB
0def12  COPY package.json package-lock…   8.1kB
345678  WORKDIR /app                      0B

Read it bottom-up: that is the build order. Read the SIZE column and you can see immediately where the weight is. CMD weighs nothing because it only changes metadata in the config document, not the filesystem.

The cache key is content, not time

Docker caches each layer. On a rebuild it walks the Dockerfile top-down and reuses a cached layer when both of these match:

  1. the instruction itself (the exact text), and
  2. the content of any files the instruction reads (COPY/ADD sources).

The moment one layer misses, every layer after it is rebuilt. There is no per-layer independence — this is the behaviour people most often mispredict.

That gives you one rule for Dockerfile ordering:

Put the things that change rarely at the top, and the things that change often at the bottom.

Now a source edit rebuilds in under a second instead of reinstalling the world. Note that RUN instructions change their cache key only via the instruction text — which is why RUN apt-get update && apt-get install -y curl should be a single layer, and why the notorious RUN apt-get update in its own line can cache stale package indexes for weeks.

Watch out

Cached package indexes are a real incident source. A build that installs from a cached apt-get update can install versions from months ago and pass CI while the fresh deploy fails. If you need freshness, invalidate deliberately: combine update and install in one RUN, or bust the cache with a build argument.

Better still is a multi-stage build, where the compiler never enters the final image at all:

The second stage starts from a clean base, so only the artifacts you explicitly copy exist. Build tooling, source files and test fixtures simply are not there.

Tags are mutable; digests are not

For anything you will have to explain during an incident, pin the digest. A tag in a deploy manifest means two replicas can be running different code without anyone having changed anything — one of the least fun failure modes to diagnose under pressure.

Check yourself

The quiz asks you to predict which change invalidates which layer. That prediction is the skill: it is what stops you from rebuilding a 141 MB dependency layer because you fixed a typo in a comment.

Command cheat sheet

Each entry is the syntax, a real invocation with the output to expect, the failure it hides and where it behaves differently on another system.

docker history <image>

Show each layer and the instruction that created it.

docker build -t app .

Build, reusing cached layers where possible.

docker save <image> -o img.tar

Export the image layers for inspection.

docker image prune

Remove dangling layers left behind by rebuilds.
